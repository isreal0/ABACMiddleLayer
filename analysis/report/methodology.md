# Methodology

## Canonical corpus

10 hand-authored scenarios (`benchmark/corpus/canonical/scenarios.json` in
the harness repo) in a University of Auckland "course score" domain — a
student's score in a specific course — chosen to match the
`/UOA_CANVAS_LMS/` prefix already hardcoded in the Middle Layer's
pre-existing C integration, rather than a generic researcher/dataset
example. Scenarios cover:

- Permit, Deny, and NotApplicable decisions
- Owner-based, role-based, and department-based rules
- Numeric clearance/classification comparison
- Time-of-day and network conditions
- Set-membership on action
- `permit-overrides` combining (used throughout; deny-overrides and
  first-applicable are not yet separately demonstrated — see
  `threats-to-validity.md`)

Ground truth was derived against one hand-authored XACML 3.0 reference
policy (`benchmark/corpus/reference-policies/xacml3-course-score-policy.xml`),
then **translated, not re-derived**, into the other engines' native
formats:

- XACML 2.0 for SunXACML (`xacml2-course-score-policy.xml`) — necessarily
  different Target/Condition syntax (Subjects/Resources/Actions/
  Environments with category-specific AttributeDesignators; XACML 2.0 has
  no generic Category-attributed AttributeDesignator), same semantics.
- A single Exprtk matcher expression for Casbin-CPP
  (`casbin-model.conf`) — Casbin has no per-rule Target/Rule/combining-
  algorithm structure at all, so the same three permit-conditions were
  OR'd into one boolean expression instead of a translated rule tree.

See `docs/semantic-mapping.md` in the harness repo for the full
per-feature translation table and the fixed AttributeId naming convention
(`urn:uoa:canvas:*`) every adapter reproduces.

## Policy-scale tiers

Three tiers, generated by `benchmark/scripts/generate-corpus.py`:

- **small** — 0 decoy rules (the original policy as authored)
- **medium** — 1000 decoy rules/rows
- **large** — 5000 decoy rules/rows

A decoy rule/row is drawn from one of three structurally-varied,
realistic shapes (role+network / department+clearance / action+hour),
using values from real pools (15 departments, 10 roles, 5 networks,
clearance/hour thresholds), generated via a **fixed-seed RNG (260825)**
so all four VMs produce byte-identical decoy content from the same
corpus commit. Every decoy is `Effect="Deny"`: under `permit-overrides`,
a Deny-effect rule can never flip an expected Permit (any matching Permit
rule always wins), and every canonical scenario's expected Deny is
already the policy's own default — so decoys are safe to let
coincidentally match a real scenario's attributes, which is what makes
them realistic instead of deliberately unreachable filler.

This design supersedes, rather than reuses, the pre-existing
`policy1k`/`policy5k` directories found in the repository at the start of
this work — those were earlier, ungoverned attempts at scale testing not
produced by the canonical-corpus pipeline (see `docs/architecture.md`).

## Benchmark protocol

Defined once in `benchmark/benchmark-manifest.conf`, consumed identically
by every engine's runner (never hard-coded per-runner, per the master
guide's explicit requirement):

```
warmup_iterations=5
measured_iterations=20
repetitions=3
random_seed=260825
concurrency_levels=1,2,4,8
```

These are deliberately small relative to the master guide's suggested
figures (warmup=1000, measured=10000): AuthzForce's CLI has no batch
mode, so every call is an independent JVM process taking 1-5 seconds at
the scales tested, and guide-scale iteration counts would take hours per
engine. See `threats-to-validity.md`.

**Sampling**: each measured call round-robins through all 10 canonical
scenarios (not repeatedly sampling one scenario). This matters
mechanically: an early single-sample pass repeatedly evaluated only one
Permit scenario, which short-circuits under `permit-overrides` before
ever reaching a policy's decoy rules — producing a misleadingly flat/
noisy scale-vs-latency trend. Round-robin sampling, which necessarily
includes Deny scenarios that must scan every remaining rule, produced a
clean monotonic trend on every engine once corrected.

**Timing separation**: for the three in-process engines (Middle Layer,
SunXACML, Casbin-CPP), a warm-up call isolates one-time policy-load cost
from per-call `evaluation_ns` (each engine's PDP/Enforcer caches its
parsed policy for the life of the process). AuthzForce's CLI has no such
separation available — every subprocess call re-parses from scratch, so
`total_ns` there is JVM startup + load + evaluation, inseparably.

**Concurrency**: Middle Layer and SunXACML share one engine instance
across a fixed-size thread pool (matching how a real long-running PDP
service is actually hit by concurrent requests). AuthzForce and
Casbin-CPP use independent OS processes instead — AuthzForce because it
has no batch mode at all, Casbin-CPP because `Enforcer::Enforce()` proved
not thread-safe even with one instance per thread (see `correctness.md`).
Aggregate throughput is measured requests ÷ wall-clock time of the whole
concurrent batch, not the reciprocal of mean per-call latency, which does
not reflect real concurrent throughput.

## Aggregation

Raw per-request latencies (`analysis/raw/<engine>/*.tsv`) and normalized
correctness/benchmark records (`analysis/normalized/*.jsonl`,
`*.benchmark.json`) were copied from each VM's `/opt/abac-research/results/`
into this repository without deleting the server-side originals, per the
master guide's Step 6 instruction. Every number in this report traces to
one of those files.
